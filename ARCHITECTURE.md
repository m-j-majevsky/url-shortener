## Слоистая архитектура

```
handler → service → repository → pgx → PostgreSQL
                   ↘ (альтернатива) LocalStorage → файл состояния
handler/service → audit.Broadcaster → FileSink / HTTPSink
```

1. **handler** — HTTP-хендлеры на chi. Не импортирует `repository`: сервис
   принимает через композитный интерфейс `Shortener`, собранный из мелких
   интерфейсов (`ShortURLCreator`, `BatchShortURLCreator`, `ShortURLGetter`,
   `UserURLsLister`, `UserURLsDeleter`, `UndeleteFinalizer`, `Pinger`,
   `UserRegistrator`). Хендлер работает только с sentinel-ошибками из `service`.
2. **service** — бизнес-логика: генерация токенов, ретраи занятых токенов,
   трансляция ошибок хранилища в сервисные, пакетное сохранение с частичным
   успехом и откатом, асинхронная очередь удалений. Транслирует ошибки
   `repository` в собственные (`service.ErrTokenNotFound` и т. д.) — наружу
   протекают только типы сервиса.
3. **repository** — две реализации одного контракта: `pgStorage` на pgx v5
   (за приватным интерфейсом `dbtx`, реализуемым и пулом, и моком pgxmock)
   и `LocalStorage` — in-memory с сохранением состояния в JSON-файл.
4. **audit** — паттерн «Наблюдатель»: асинхронная рассылка событий приёмникам.

## Логирование

Логирование построено на `go.uber.org/zap` без глобальных переменных.
`logger.Initialize` создаёт корневой логгер, в `main` от него создаются дочерние
с полем `component`:

| Компонент | Кому передаётся |
|---|---|
| `main` | запуск, instance lock, shutdown |
| `server` | запуск и остановка HTTP-сервера |
| `handler` | роутер и middleware логирования |
| `service` | `Shortener`, процессор удалений |
| `audit` | `Broadcaster` |

Если логгер не передан — компонент использует `zap.NewNop()`.

## Схема базы данных

Две таблицы, четыре миграции (все встроены в бинарник через `go:embed`).

### Таблица `shorten_urls`

| Колонка | Тип | Назначение |
|---|---|---|
| `id` | `uuid PRIMARY KEY DEFAULT gen_random_uuid()` | идентификатор записи |
| `token` | `text NOT NULL` | короткий токен, `UNIQUE (shorten_urls_token_key)` |
| `original_url` | `text NOT NULL` | исходный URL, `UNIQUE (shorten_urls_original_url_key)` — миграция 0002 |
| `user_id` | `uuid` (nullable) | владелец — миграция 0003 |
| `created_at` | `timestamptz NOT NULL DEFAULT now()` | время создания |
| `is_deleted` | `boolean NOT NULL DEFAULT FALSE` | мягкое удаление — миграция 0004 |

Индекс: `idx_shorten_urls_user_id` — для листинга ссылок пользователя.

Уникальность `original_url` **глобальная**: один и тот же URL не может быть
сохранён дважды. Повторное сохранение возвращает старый токен (ответ 409 с телом),
а не создаёт дубль.

### Таблица `users`

| Колонка | Тип | Назначение |
|---|---|---|
| `id` | `uuid PRIMARY KEY DEFAULT gen_random_uuid()` | идентификатор пользователя |
| `created_at` | `timestamptz NOT NULL DEFAULT now()` | время регистрации |

Пользователи анонимны (логина/пароля нет): JWT с ID пользователя выдаётся
`CookieMiddleware` при первом запросе.

### Про историю схемы

Внешний ключ `user_id → users(id)` **закомментирован** в миграции 0003
с пояснением: процедура зачистки тестовых сценариев платформы Практикума в
GitHub Actions не задействует down-скрипты миграций, из-за чего FK приводил
к проблемам при проверке ранних инкрементов. Целостность по владельцу
гарантируется кодом приложения.

## xmax-трюк распознавания конфликтов

Ключевая техника слоя хранилища. Потребность: при вставке уже существующего
`original_url` нужно вернуть **старый** токен, но `ON CONFLICT DO NOTHING`
не даёт `RETURNING`, а `DO UPDATE` перезаписывает строку.

```sql
INSERT INTO shorten_urls (token, original_url, user_id)
VALUES ($1, $2, $3)
ON CONFLICT (original_url) DO UPDATE
SET original_url = EXCLUDED.original_url
RETURNING token, (xmax = 0) AS was_insert
```

- `xmax = 0` только у свежевставленной строки; после `DO UPDATE` (даже
  холостого обновления тем же значением) `xmax` ненулевой — была перезапись.
- `was_insert = false` → URL уже был сохранён: возвращаем `ErrOriginalURLExists`
  с токеном из `RETURNING`. Условия у `DO UPDATE` нет, поэтому трюк работает
  и для удалённых (`is_deleted`) строк — их `is_deleted` не трогается.
- Конфликт по `token` (занятый токен) уникальным конфликтом по `original_url`
  не ловится — он падает ошибкой `UniqueViolation` с constraint-именем
  `shorten_urls_token_key`, которое различается по коду `pgerrcode`.

Семантика проверена юнит-тестами на pgxmock и интеграционными тестами на живой
PostgreSQL, включая точную копию удалённой строки.

## HTTP-хендлеры

### Middleware-цепочка

`logger.WithLogging` → `GzipMiddleware` → (для защищённой группы) `CookieMiddleware`.

- **GzipMiddleware** действует только для запросов с `Content-Type`
  `text/plain` или `application/json`. Ответы сжимаются, если клиент прислал
  `Accept-Encoding: gzip`; gzip-тело запроса распаковывается, невалидный
  gzip-поток — 400. Gzip применяется только к ответам с кодом < 300 и телом
  (204 и 304 уходят без сжатия — закрытие gzip.Writer дописало бы в пустой
  ответ gzip-заголовок и футер).
- Ограничения тела: `POST /` — 2048 байт, JSON-эндпоинты — 4096 байт,
  батч — до 1 МБ.

### `CookieMiddleware` — аутентификация

Аутентификация по cookie с JWT (HS256, ключ из `SIGNING_KEY`, TTL 24 часа):

1. Cookie нет или JWT невалиден → регистрируется новый пользователь
   (`CreateUser`), выдаётся новая cookie (`HttpOnly`, `SameSite: Strict`,
   `Secure` для HTTPS, `Path: /`).
2. Валидный JWT с пустым ID → **401** без вызовов хранилища.
3. Валидный непустой JWT → `CheckUserExists`: не найден → **401**, ошибка → **500**.
4. `userID` кладётся в контекст запроса (`user_id`) для хендлеров группы.

Защищённая группа: `POST /`, `POST /api/shorten`, `POST /api/shorten/batch`,
`GET/DELETE /api/user/urls`. Вне группы: `GET /{token}` и `GET /ping`.

### `POST /` — сокращение URL (text/plain)

1. Чтение тела (до 2048 байт), обрезка пробелов.
2. `service.GenerateAndStore`.
3. **201** с телом `{baseURL}/{token}`; `ErrOriginalURLExists` → **409**
   с телом `{baseURL}/{старый токен}` (токен приходит из `xmax`-трюка);
   прочее → **500**.
4. Аудит `shorten` отправляется и на 201, и на 409.

### `POST /api/shorten` — сокращение URL (JSON)

1. Проверка `Content-Type: application/json` — иначе **400**.
2. Чтение JSON (до 4096 байт), разбор и валидация (`url` — валидный URL) —
   **400** при нарушениях.
3. Далее как в text/plain: 201 / 409 / 500, аудит `shorten`.

### `POST /api/shorten/batch` — пакетное сокращение

1. Проверка `Content-Type` и валидации каждого элемента (`correlation_id`
   непуст, `original_url` — валидный URL) — **400**.
2. `service.BatchStore` (см. «Пакетное сохранение и откат»).
3. Ответ **201** со списком `{correlation_id, short_url}`; при наличии
   `ConflictedURL` в результате — **409**, конфликтным элементам
   возвращается старый токен; ошибка сервиса — **500**.

### `GET /{token}` — редирект

1. Валидация токена по base62 (не-ASCII и прочие символы — **400**; маршруты
   вне шаблона `/{token}` — **400** «недопустимый путь в URL», чужой метод —
   **400** «недопустимый метод»).
2. `service.Resolve`: **307** с заголовком `Location`; `ErrTokenNotFound` →
   **400**; `ErrTokenIsDeleted` → **410**; прочее → **500**.
3. Аудит `follow` с пустым `user_id` (запрос вне защищённой группы).

### `GET /api/user/urls` — список ссылок пользователя

`service.ListUserURLs` (не удалённые записи владельца). Пусто → **204**;
не пусто → **200**, JSON-массив `{short_url, original_url}` с проставленным
базовым префиксом; ошибка → **500**.

### `DELETE /api/user/urls` — удаление ссылок

1. Проверка `Content-Type` и валидация токенов (base62) — **400**.
2. `service.MarkUserURLsDeleted`: постановка в очередь удалений.
3. Ответ всегда **202** — удаление асинхронное, клиенту не обещается
   немедленный результат. При ошибке постановки (переполнение/закрытая очередь)
   пары дозаписываются в dead-letter через
   `HandleErrTokenLeftUndeletedAndLogData`, код ответа не меняется.

### `GET /ping` — проверка хранилища

`service.Ping`: **200** при успехе, **500** при недоступности хранилища.
Без аутентификации.

## Бизнес-логика сервиса

### Генерация токенов

`generateTokens(n)`: на каждую попытку берётся 6 случайных байт из
`crypto/rand` (провайдер `crypto.RandomByteProvider` — подменяется в тестах),
кодируется в base62 (`encoding.EncodeToBase62`). Подходящим считается токен
длиной 6–10 символов; повторы внутри пакета отбрасываются. Всего не более
`MaxGeneratingAttempts × n` попыток; иначе — ошибка с параметрами.

### Ретраи и конфликты

`GenerateAndStore` до `MaxStoringAttempts` (10) раз генерирует токен и пытается
сохранить. `ErrTokenTaken` (токен занят другим URL) — повторная попытка с новым
токеном; `ErrOriginalURLExists` — немедленный возврат старого токена
(сервис транслирует ошибку хранилища в сервисную); прочие ошибки — наверх
с обёрткой.

### Пакетное сохранение и откат

`BatchStore` реализует **частичный успех**: на каждой попытке хранилище
возвращает батч с признаками конфликтов (`ConflictedToken` — занятый токен,
`ConflictedURL` — URL уже сохранён).

1. Элементы, сохранённые или конфликтующие по URL, накапливаются в `stored`;
   занятые токены идут на повторную попытку с новыми токенами (с сохранением
   `CorrelationID`).
2. Если после попытки все элементы покрыты (`len(stored) == len(req)`) —
   успех, даже если часть из них конфликты по URL.
3. Прочая ошибка хранилища или исчерпание попыток → `restoreWithError`:
   жёсткое удаление (`DeleteByTokens`) всех записей, **сохранённых этим
   запросом** — конфликтные по URL исключаются из отката (чужой токен не
   трогается). Ошибка отката склеивается с исходной через `errors.Join` —
   ни одна часть не теряется.

## Асинхронный конвейер удалений

### Очередь и процессор

`DELETE /api/user/urls` не выполняет удаление синхронно: пары
(токен, пользователь) уходят в `deletionQueue` (`chan`, буфер 1024). Отправка —
`select` с `default`: переполнение очереди не блокирует запрос, элементы
получают `ErrTokenLeftUndeleted`.

`StartItemsDeletionProcessor` — горутина, запускаемая из `main` (не из
конструктора сервиса: конструктор только создаёт очередь). Процессор
накапливает батч и сбрасывает его в хранилище (`MarkUserURLsDeleted` — мягкое
`UPDATE ... SET is_deleted = TRUE`) по двум триггерам:

1. размер батча достиг `DeletionBatchSize` (1024);
2. `time.Ticker` каждые `DeletionQueueFlushTimeout` (10 с).

Каждый флаш выполняется в отдельной горутине с контекстом
`context.WithoutCancel(ctx)` — отложенные удаления доводятся до хранилища даже
при остановке сервиса по сигналу (пул соединений закрывается позже).

### Dead-letter

Ошибки хранилища при пакетном удалении не теряют данные: соответствующие пары
дозаписываются в dead-letter-файл (JSON-lines: `token`, `user_id`,
`discarded_at`). Путь задаётся флагом `-dead-letter-file` или переменной
окружения `DEAD_LETTER_FILE`; по умолчанию — `emergency_dead_letter.log` во
временном каталоге ОС (абсолютный путь, учитывает `TMPDIR`). В systemd или
контейнере временный каталог волатилен — для сохранности журнала укажите путь
на постоянном томе.

Файл открывается при первой записи (`O_APPEND|O_CREATE`), закрыт при `CleanUp`.
Записываемость пути проверяется при старте: недоступный файл отказывает запуск
с внятной ошибкой вместо тихой потери записей в момент сбоя. Ошибки записи
логируются на обоих путях вызова — в хендлере и в процессоре удаления.
Записи могут быть обработаны вручную после инцидента.

### Graceful stop

1. `StopItemsDeletionProcessor` закрывает канал. Отправка в закрытый канал
   дала бы панику «send on closed channel», поэтому закрытие защищено мьютексом
   и флагом `deletionQueueClosed`: хендлеры «в полёте» получают
   `ErrTokenLeftUndeleted` штатным путём ошибки.
2. Процессор дочитывает накопленный батч, делает финальный флаш
   (`storageWg.Wait`) и завершается.
3. Повторный `StopItemsDeletionProcessor` безопасен.

## Аудит

Паттерн «Наблюдатель» (`internal/audit`):

- **Событие** `AuditEvent{ts, action, user_id, url}`; действия: `shorten`
  (создание ссылки, и на 201, и на 409) и `follow` (переход по короткой ссылке).
- **Broadcaster** — «субъект»: один диспетчер читает входной канал
  (буфер 1024) и раскладывает события в личные очереди наблюдателей
  (буфер 64 каждая); на каждого наблюдателя — свой воркер. Медлительность
  одного приёмника не блокирует ни обработку запроса, ни доставку другим.
  Ошибки отправки логируются. Число отброшенных из-за переполнения событий
  учитывается атомарным счётчиком `Dropped()`.
- **Приёмники**: `FileSink` (дозапись JSON-lines в файл, `O_APPEND`) и
  `HTTPSink` (POST JSON на URL, таймаут 5 с, статус ≥ 400 — ошибка).
  Без наблюдателей `Notify` — no-op.
- **Безопасность при shutdown**: `Notify` защищён флагом `closed` под
  `RWMutex` — его можно вызывать, даже когда `server.Shutdown` завершился
  по таймауту и хендлеры продолжают работу. При остановке `Close()`
  дожидается доставки с дедлайном 10 с; по истечении дедлайна приёмники
  **сознательно не закрываются** — закрытие файла посреди записи воркером
  дало бы ошибки.

## Graceful shutdown

Последовательность при получении SIGINT/SIGTERM:

1. Отмена сигнального контекста → `server.Shutdown` (до `ShutdownTimeout` = 10 с).
2. `StopItemsDeletionProcessor` — закрытие очереди удалений; процессор
   доводит накопленный батч до хранилища.
3. `backgroundWg.Wait()` — процессор завершён.
4. `auditor.Close()` с дедлайном 10 с — доставка накопленных событий аудита.
5. Закрытие приёмников аудита (только реализующих `io.Closer`).
6. Деферы `main`: сохранение состояния LocalStorage (файловый режим),
   `pg_advisory_unlock` и закрытие пула, снятие `flock`.

Ошибки запуска сервера (например, занятый порт) не теряются в горутине:
`ListenAndServe` отправляет ошибку в канал, который читает `main`, — иначе
сервис оставался бы живым, но не отвечающим.

## Single-instance enforcement

Реализация рассчитана на один инстанс; одновременный запуск двух процессов
приводит к потере данных (в файловом режиме) и неопределённому поведению.
Защита:

- **Режим БД:** `pg_try_advisory_lock(20260101)` на выделенном коннекте пула —
  session-level lock, держится, пока жив коннект; при падении процесса
  PostgreSQL снимает его автоматически. Захват до `RunMigrations`, чтобы
  исключить параллельный запуск миграций. Отсутствие lock — запуск отменяется.
- **Файловый режим:** эксклюзивный `flock` (`LOCK_EX|LOCK_NB`) на файл
  `<путь состояния>.lock`. Отдельный lock-файл нужен, чтобы не создавать сам
  файл состояния: `LoadFromFile` отличает «файла нет — стартуем с пустого
  хранилища» от битого содержимого.
- **Локальное хранилище без файла:** блокировка не нужна — файла состояния
  нет, конфликт портов и так не даст запуститься второму экземпляру
  на том же адресе.
