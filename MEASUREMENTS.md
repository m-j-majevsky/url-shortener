# Измерения: методика и журнал

Файл-журнал оптимизации сервиса. Здесь фиксируются: методика измерений, базовая
линия до оптимизаций и результаты после каждого кандидата. Числа в таблицах
заполняются по ходу работы — шаблоны оставлены пустыми.

## Инструменты

| Инструмент | Запуск | Что даёт |
|------------|--------|----------|
| Микробенчмарки Go | `make bench` | Время, память и аллокации на операцию по четырём пакетам |
| loadgen | `make loadgen`, затем `bin/loadgen ...` | Нагрузочный прогон: rps и разбивка ответов по HTTP-кодам |
| benchstat | `go install golang.org/x/perf/cmd/benchstat@latest` | Статистически корректное сравнение «до/после» по файлам результатов |
| pprof-эндпоинт | запуск сервиса с `PPROF_ADDR=localhost:6060` | Снимки cpu/heap/goroutine под живой нагрузкой: `curl` на `/debug/pprof/*` |

Полный список флагов loadgen — `bin/loadgen -h`. Ключевые флаги:

- `-mode` — профиль нагрузки: `post` (создание ссылок), `get` (переходы по токенам
  с прогрева), `batch` (пакетное создание, размер пакета — `-batch`);
- `-n` — число запросов измеряемой фазы (длительность прогона — производная:
  зависит от числа воркеров и времени ответа сервера);
- `-c` — число конкурентных воркеров;
- `-warmup` — сколько URL засеять до измеряемой фазы; прогрев требует ответ
  201 — любой не-201 приводит к `exit(1)`, поэтому повторный get-прогон того
  же сида на живом сервере невозможен (сервер перезапускается);
- `-batch` — элементов в пакете (только `mode=batch`);
- `-seed` — базовый сид генератора (см. «Детерминизм» ниже).

## Базовая линия

Снимается на чистой рабочей копии (без незакоммиченных изменений) до первых
правок. Порядок:

1. Микробенчмарки, быстрый прогон для ориентира:

   ```
   make bench | tee bench_before.txt
   ```

2. Микробенчмарки для benchstat (повторы обязательны, без них сравнение
   недостоверно):

   ```
   go test -run='^$' -bench=. -benchmem -count=10 \
     ./internal/encoding/ ./internal/service/ \
     ./internal/repository/ ./internal/handler/ | tee bench_stat_before.txt
   ```

3. Сборка и нагрузочные прогоны. Сервер — на локальном хранилище (без
   `DATABASE_DSN`, см. «Правила» ниже). Порядок: post → get → batch; перед
   каждой группой — свежий сервер; вторые прогоны post и batch — без
   перезапуска (все URL уже в хранилище — замер проверки дубликатов).

   ```
   mkdir -p profiles/loadgen
   make run 2>&1 | tee profiles/loadgen/server_before.log

   bin/loadgen -mode=post  -c=4 -n=20000 -warmup=0                   -seed=1 | tee profiles/loadgen/post_run1_before.txt
   bin/loadgen -mode=post  -c=4 -n=20000 -warmup=0                   -seed=1 | tee profiles/loadgen/post_run2_before.txt
   # перезапуск сервера
   bin/loadgen -mode=get   -c=4 -n=20000                             -seed=1 | tee profiles/loadgen/get_run1_before.txt
   # перезапуск сервера
   bin/loadgen -mode=get   -c=4 -n=20000                             -seed=1 | tee profiles/loadgen/get_run2_before.txt
   # перезапуск сервера
   bin/loadgen -mode=batch -c=4 -n=4000 -warmup=0 -batch=5           -seed=1 | tee profiles/loadgen/batch_run1_before.txt
   bin/loadgen -mode=batch -c=4 -n=4000 -warmup=0 -batch=5           -seed=1 | tee profiles/loadgen/batch_run2_before.txt
   ```

   Замечания: в batch 4000 запросов × 5 элементов = 20 000 вставок — тот же
   масштаб, что в post; вывод loadgen — только итоговая строка rps и разбивка
   по HTTP-кодам, промежуточных значений нет.

4. Если кандидат затрагивает аллокации, снять heap-снимок «до» под нагрузкой
   pprof-эндпоинта (сервер запускается с `PPROF_ADDR`); разность снимков
   «до/после» строит `go tool pprof -diff_base`:

   ```
   curl -o profiles/heap_before.pb.gz "http://localhost:6060/debug/pprof/heap"
   ```

## Правила корректного сравнения

- **Сиды фиксированы.** `-seed=1` во всех прогонах. Прогрев идёт от базового
  сида, воркеры измеряемой фазы — от `seed + 1_000_000 + номер воркера`:
  состав запросов между прогонами воспроизводим, поэтому `benchstat`
  корректен, а heap-снимки «до/после» сопоставимы (разность — `go tool
  pprof -diff_base`).
- **Пространства URL не пересекаются.** Прогревочные запросы живут в хостах
  `*.seed`, измеряемые — в `*.bench`. Смешивание дало бы ложные ответы 409
  (повторное сокращение того же URL) и испортило бы обе части замера.
- **Флаг `-base` соответствует `BASE_URL` сервера.** При нестандартном
  `BASE_URL` генератор нужно запускать с тем же `-base`, иначе в режиме `get`
  все запросы пойдут по ложному префиксу и вернут ошибки, а не время ответа.
- **Хранилище базовой линии — локальное.** Сервер запускается без
  `DATABASE_DSN` (выбор в `cmd/shortener/main.go`: непустой DSN — PostgreSQL,
  иначе `LocalStorage`). Кандидаты оптимизации № 1–2 правят путь
  `LocalStorage`: под Postgres эффект растворится в сетевых и БД-задержках.
  Сравнение до/после — только на одном и том же типе хранилища.
- **Прогрев требует 201.** Любой не-201 в прогреве — `exit(1)` утилиты.
  Прогревочные URL записываются в хранилище, поэтому get-прогон повторяется
  только на свежем сервере.
- **Вывод loadgen — только итоговый.** Промежуточных значений утилита не
  печатает; деградация по мере наполнения хранилища видна по паре
  run1/run2, а не по траектории внутри прогона.
- **Детерминизм при `-c > 1` — частичный.** Сиды воркеров фиксированы, но
  распределение заданий между воркерами — гоночный фактор: множества URL
  двух прогонов совпадают лишь частично (при `-c=4` — около 94%). Сравнения
  по нагрузке считаем по средним rps; для строгого состава запросов —
  `-c=1`. Прогрев однопоточный и воспроизводим точно.
- **Серверный лог — сэмплированный.** `zap.NewProductionConfig()` включает
  встроенный сэмплер: после первых 100 записей на пару (сообщение, уровень)
  пишется каждая сотая. В лог попадает лишь малая доля запросов, доли кодов
  в логе не совпадают с фактическими. Счёт ответов — только из вывода
  loadgen; серверный лог — источник серверных длительностей и фона.
- **Редирект не ходит наружу.** loadgen не следует за 307 — переходы не уходят
  в сеть и не искажают время ответа.
- **Бенчи вставки меряют среднюю цену в растущем хранилище.** `Store` и
  `GenerateAndStore` добавляют записи по ходу прогона: к концу замера в
  хранилище `b.N + preseed` записей, и ns/op — средняя цена по всему прогону,
  а не фиксированная величина. Абсолютные числа зависят от benchtime; сравнение
  до/после корректно только при одинаковом benchtime (держим значение по
  умолчанию в обеих точках).
- **benchstat — только по файлам с повторами.** Одиночный прогон `go test
  -bench` показывает порядок величин, но шум на малых значениях велик;
  выводы по кандидатам делаются по `-count=10` и выводу benchstat
  (`benchstat bench_stat_before.txt bench_stat_after.txt`).
- **Машина в простое.** На время прогонов закрываются браузеры, IDE-индексация
  и прочий фон; иначе дельты будут отражать соседние процессы, а не правки.
- **Одна переменная за раз.** Каждый кандидат оптимизации оценивается
  отдельной парой прогонов; комбинированные правки не позволяют понять,
  что именно дало эффект.
- **Контроль качества замера.** `Resolve` в bench-файле репозитория —
  контрольная группа: поиск по ключу мапы не зависит от объёма хранилища.
  Если его числа «плывут» между прогонами — замер загрязнён чем-то посторонним.

Выводы по базовой линии (куда смотреть в первую очередь):

1. **Контрольная группа здорова.** `Resolve`: 98 → 106 нс/op при росте preseed
   1k → 5k — колебания в пределах шума (CV до 4%), аллокации не растут.
   Замер чистый, рост соседних чисел — реальный эффект, а не загрязнение.
2. **Подтверждён O(n)-перебор в `LocalStorage.Store`.** Проверка уникальности
   original_url идёт полным проходом по значениям мапы (`map_based_storage.go`,
   перебор `s.data` без индекса). Виден по росту с preseed: 106 → 114 → 178 мкс
   при 0 → 1k → 5k. Тот же эффект тянется в `GenerateAndStore` (114 → 140 →
   190 мкс) и в `BatchStore` (там перебор на каждый элемент батча).
   Кандидат №1 — индекс original_url → token: O(n) → O(1).
3. **Методологическое примечание по Store-бенчам.** Бенчи вставки пишут записи
   по ходу прогона: к концу замера в хранилище `b.N + preseed` записей, а
   ns/op — средняя цена вставки в растущее хранилище. Поэтому абсолютные
   значения зависят от benchtime (дымовой прогон на `-benchtime=10x` дал 890 нс
   против 106 мкс здесь). Сравнение до/после корректно только при одинаковом
   benchtime — держим значение по умолчанию в обеих точках замера.
4. **Gzip — главная находка handler'а.** 815 КБ/оп на каждый сжатый ответ —
   стабильная величина (совпадает с дымовым прогоном, где B/op был тем же), то
   есть это реальные аллокации, а не прогрев: `gzip.NewWriter` создаёт на каждый
   сжатый ответ внутренние буферы `compress/flate` — hash-таблицу (~512 КБ) и
   окно (~32 КБ). Высокое время (207 мкс, CV 13%) — в значительной части
   GC-давление от этого потока памяти. Кандидат №2 — `sync.Pool` для
   gzip.Writer: снимет аллокации целиком и часть времени.
5. **Логирование дёшево.** nop 1.9 мкс, dev_null 3.8 мкс — разница ~2 мкс —
   цена формирования JSON-записей; `FullChain` (180 мкс) почти целиком состоит
   из gzip, вклад логирования несущественен.
6. **Encoding в оптимизации не нуждается.** `EncodeToBase62` — 336 нс, 4
   аллокации; `IsValidBase62` — 11 нс, 0 аллокаций. Не трогаем.

### Нагрузка — базовая линия

Дата: 2026-10-29. Хранилище: локальное, сервер свежий перед каждой группой;
run2 post/batch — без перезапуска (профиль проверки дубликатов). Файлы
прогонов — `profiles/loadgen/*_before.txt`, логи сервера — там же.

| Прогон | c | n | warmup | rps | 2xx | прочие коды |
|--------|---|---|--------|-----|-----|-------------|
| post run1 | 4 | 20000 | 0 | 1311 | 201: 20000 | — |
| post run2 | 4 | 20000 | 0 | 2800 | 409: 18825 | 201: 1175 |
| get run1 | 4 | 20000 | 5000 | 11285 | 307: 20000 | — |
| get run2 | 4 | 20000 | 5000 | 9905 | 307: 20000 | — |
| batch run1 | 4 | 4000 | 0 | 556 | 201: 4000 | — |
| batch run2 | 4 | 4000 | 0 | 491 | 409: 3406 | 201: 594 |

Выводы по нагрузочной базе:

1. **run2 post быстрее run1** (2800 против 1311 rps) — вопреки наивному
   ожиданию. По медианным серверным длительностям из логов: вставка (окно
   run1) ≈ 387–406 мкс, проверка дубликата (окно run2) ≈ 204–231 мкс. Оба
   прогона несут O(n)-скан; вставка дороже ещё примерно на 200 мкс HTTP-пути
   и вставки. Значит, кандидат № 1 снимет скан с обоих путей, но потолок
   post ограничен и дорогой вставки — она станет следующим узким местом.
2. **get** — 11285/9905 rps, разброс ~13% между идентичными прогонами на
   свежем сервере. Это мера шума однопрогонного замера: выводы по нагрузке —
   только по различиям больше ~15%. Медианная серверная длительность get ≈
   10 мкс — O(1)-поиск подтверждён.
3. **batch** — 556/491 rps; run2 медленнее run1, но разница в пределах шума.
   Медианная длительность запроса ≈ 1,7 мс, p95 ≈ 26 мс: пять сканов на пакет
   плюс вставки. Ожидание от кандидата № 1 — кратный рост rps в обоих
   прогонах.
4. **Детерминизм частичный**: в run2 есть вставки 201 (post: 1175, batch:
   594) — распределение заданий между воркерами при `-c=4` гоночное,
   множества URL совпадают примерно на 94%. run2 — не «чистые 409», а
   ~94/6; это ограничение методики, не ошибка протокола.
5. **В логах ~7% запросов** (сэмплер zap; в g1 — 2663 из ~40 000). Счёт
   ответов — только по выводу loadgen; лог используется для серверных
   длительностей и фона.

### Профили — базовая линия

Дата: 2026-10-29. Протокол: сервер запускается с `PPROF_ADDR=localhost:6060`
(отдельный pprof-сервер); снимки `curl`-ом на `/debug/pprof/*`; файлы —
`profiles/pprof/*_before.pb.gz`. Пустой профиль проверяется по `total samples`.

Занятость CPU за окно снимка: post run1 — 9,14 с из 15 с (61%), post run2 —
4,55 с из 7 с (65%), batch run1 — 3,70 с из 5 с (74%), idle — 0 сэмплов за 7 с
(фон пуст: всё CPU — нагрузка). Остаток до 100% — ожидание (мьютексы, сеть).

| Срез (cum, с перекрытиями) | post run1 (вставки) | post run2 (409) | batch run1 |
|----------------------------|--------------------:|----------------:|-----------:|
| итерация мапы (скан) | 36,3% | 45,5% | 54,6% |
| `Store`/`BatchStore` целиком | 50,4% | 64,6% | 69,2% |
| gzip-путь (`Writer.Write`+`Close`) | ~20% | ~1% | ~1% |
| regexp (`machine.add`/`step`) | — | — | 4,6% |
| чтение тела запроса (`memeqbody`) | 8,6% | 13,8% | 8,6% |

Flat-срез (накопитель не пересекается):

| Срез (flat) | post run1 | post run2 | batch run1 |
|-------------|----------:|----------:|-----------:|
| GC и барьеры записи | 47,0% | 26,8% | 34,3% |
| скан: итерация мапы | 17,7% | 34,5% | 34,1% |
| чтение тела (`memeqbody`) | 8,6% | 13,8% | 8,6% |
| regexp | — | — | 4,6% |
| сеть/syscall | 2,7% | 3,1% | 1,9% |
| gzip/flate | 1,5% | 0,4% | 0,8% |
| zap | 0,3% | 0,7% | 0,3% |
| JSON | 0,3% | 0,4% | 0,3% |

Выводы по профилям:

1. **Скан — главный потребитель пути запроса.** Доля итерации мапы растёт от
   вставок (36%) к чистой проверке дубликатов (46%) и батчу (55%): кандидат № 1
   снимет её со всех трёх путей.
2. **GC — крупнейший flat-потребитель (47% в post run1).** Причина — аллокации:
   heap-дифф за прогон post run1 — **18,5 ГБ (~923 КБ/запрос)**, из них 80% —
   `gzip.Writer.Write` (14,8 ГБ) и 17% — `flate.compressor.init` (3,2 ГБ).
   Клиент loadgen шлёт `Accept-Encoding: gzip`, а gzip-миддлвэр оборачивает
   **все** роуты — сжатие создаётся на каждый ответ, включая POST. Отсюда
   кандидата № 2 (`sync.Pool`) затрагивает каждый запрос, а не только
   `/api/user/urls`; синергия с GC-давлением больше, чем ожидалось.
3. **zap и JSON — не цели** (≤1% flat): логирование с сэмплером дёшево.
4. **regexp 4,6% в batch** — валидация URL регуляркой на каждый элемент пакета;
   вне текущего цикла кандидатов, зафиксировано как наблюдение для будущего.
5. **CreateUser — 0,9% CPU, но берёт общий мьютекс хранилища.** Клиент loadgen
   не хранит куки → каждый запрос проходит ветку создания пользователя
   (`uuid.New` + лок). В goroutine-снимке batch горутины припаркованы именно
   на `LocalStorage.CreateUser`; в post run2 — на zap-мьютексе (запись в
   stdout-пайп `tee` сериализует запись). Живая память после прогона —
   17,65 МБ, из них `CreateUser` держит 6,49 МБ (43 781 объект).

Оценка эффекта кандидатов по профилям: кандидат № 1 снимает 36–55% cum скана и
часть GC; кандидат № 2 убирает ~80% аллокаций и, как следствие, долю flat-GC

2. **Контрольная группа здорова.** `Resolve` не изменился (−3% на

   пути, замер чист.
3. **Аномалия на пути вставки — не закрыта микробенчем.** preseed_0: +8,6%

   доминирует амортизация роста мап с нуля (rehash-аллокации — они же видны
   в B/op +111%), замаскированная раньше сканом; (б) разброс условий между
   прогонами «до» и «после» (сняты в разное время дня) — но он не объясняет
   градиент внутри одного файла. Решающая проверка — нагрузка шага 9;
   опциональный контроль — прогон `Store` с фиксированным `-benchtime`
   (например, `-benchtime=2000x`) в одной сессии «до/после».
4. **Цена индекса соответствует ожиданию.** B/op чистой вставки +~200 Б,
   allocs/op 1 → 2 — стоимость роста второй мапы; trade-off зафиксирован
   выше и не влияет на пути чтения (`StoreDuplicate`, `Resolve` — без
   роста аллокаций).
5. **BatchStore в микробенче не измеряется** — его эффект оценим только по
   нагрузке шага 9 (в базовой линии батч: 556/491 rps, p95 ≈ 26 мс).

Heap-дифф (если применимо): на шаге не снимался. Живая память после прогона
post — 17,65 МБ (база); ожидание «после» — небольшой рост на величину второй
мапы (~порядка единиц МБ на 20k записей). Сравнение — финальным шагом:
`go tool pprof -diff_base profiles/base.pprof profiles/result.pprof`.

Вывод: **принято**. Главный подтверждённый эффект — путь дубликата

### Нагрузка — после кандидата № 1
