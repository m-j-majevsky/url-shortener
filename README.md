# Сервис сокращения URL

HTTP-сервис сокращения длинных ссылок. Пользователь регистрируется автоматически
(cookie с JWT выдаётся при первом запросе), может создавать короткие ссылки по одной
и пакетами, просматривать свой список ссылок и удалять их — удаление асинхронное,
мягкое (`is_deleted`). Архитектура решения описана в [ARCHITECTURE.md](ARCHITECTURE.md).

## Описание

«url-shortener» — HTTP-сервис, реализующий сокращение ссылок: принимает исходный
URL, генерирует токен из [0-9a-zA-Z] (base62) длиной 6–10 символов и возвращает
короткую ссылку. Повторное сокращение того же URL возвращает **старый** токен
(коды 409 с телом). Переход по короткой ссылке — редирект 307.

Два режима хранилища:

- **PostgreSQL** — если задан `DATABASE_DSN`; миграции накатываются автоматически
  при старте;
- **локальное** (`LocalStorage`) — если `DATABASE_DSN` не задан. При заданном
  `FILE_STORAGE_PATH` состояние сохраняется в файл при завершении работы
  и загружается при старте; без `FILE_STORAGE_PATH` хранилище живёт только
  в памяти (персистенции нет).

Одновременно работает один инстанс: для режима БД — advisory lock в PostgreSQL,
для файлового режима — `flock` рядом с файлом состояния (см.
[ARCHITECTURE.md](ARCHITECTURE.md), «Single-instance enforcement»).

Удаление ссылок асинхронное: запрос `DELETE /api/user/urls` ставит токены во
внутреннюю очередь, фоновый процессор сбрасывает их в хранилище батчами. При
переполнении очереди или ошибке хранилища пары (токен, пользователь) дозаписываются
в dead-letter-файл. Аудит запросов (`shorten`, `follow`) отправляется в приёмники:
файловый и/или удалённый HTTP — паттерн «Наблюдатель».

## Требования к окружению

- **ОС:** Linux, macOS (файловая блокировка использует `syscall.Flock`)
- **Go:** версии, указанной в `go.mod`
- **PostgreSQL:** 13+ (для режима БД; `gen_random_uuid()` встроен с версии 13)
- **mockery:** v3 (для регенерации моков; `go install github.com/vektra/mockery/v3@latest`)


### Сборка вручную

```bash
go build -o ./bin/shortener ./cmd/shortener
```

### Запуск сервиса

Режим PostgreSQL:

```bash
SIGNING_KEY="ваш-секрет" ./bin/shortener -a :8080 -b http://localhost:8080 \
  -d "postgres://url_shortener:SECRET@localhost:5432/url_shortener?sslmode=disable"
```

Локальное хранилище с персистенцией (`FILE_STORAGE_PATH`):

```bash
./bin/shortener -a :8080 -b http://localhost:8080 -f /tmp/url-shortener-state.json
```

Локальное хранилище без персистенции (только память):

```bash
./bin/shortener -a :8080 -b http://localhost:8080
```

## Конфигурация

Конфигурация загружается из двух источников. **Приоритет (от низшего к высшему):**

1. Жёстко заданные значения по умолчанию
2. Флаги командной строки — перекрывают значения по умолчанию
3. Переменные окружения — перекрывают флаги

### Флаги командной строки

| Флаг | Описание | Значение по умолчанию |
|---|---|---|
| `-a` | Адрес и порт запуска HTTP-сервера | `:8080` |
| `-b` | Базовый URL сокращённых ссылок | `http://localhost:8080` |
| `-l` | Уровень логирования (`debug`, `info`, `warn`, `error`) | `info` |
| `-d` | Строка подключения к PostgreSQL (включает режим БД) | (нет) |
| `-f` | Путь к файлу состояния локального хранилища | (нет) |
| `-u` | Имя cookie с JWT пользователя | `user_id_jwt` |
| `-s` | Интервал сохранения состояния (резерв, не потребляется) | `1s` |
| `-audit-file` | Путь к файловому приёмнику аудита | (нет, аудит отключён) |
| `-audit-url` | URL удалённого приёмника аудита | (нет, аудит отключён) |

### Переменные окружения

| Переменная | Описание | Значение по умолчанию |
|---|---|---|
| `SERVER_ADDRESS` | Адрес и порт запуска HTTP-сервера | `:8080` |
| `BASE_URL` | Базовый URL сокращённых ссылок | `http://localhost:8080` |
| `LOG_LEVEL` | Уровень логирования | `info` |
| `DATABASE_DSN` | Строка подключения к PostgreSQL | (нет) |
| `FILE_STORAGE_PATH` | Путь к файлу состояния | (нет) |
| `COOKIE_USER_ID` | Имя cookie с JWT пользователя | `user_id_jwt` |
| `SIGNING_KEY` | Ключ подписи JWT-токенов | (нет; см. ниже) |
| `AUDIT_FILE` | Путь к файловому приёмнику аудита | (нет) |
| `AUDIT_URL` | URL удалённого приёмника аудита | (нет) |
| `SAVE_STATE_INTERVAL` | Интервал сохранения состояния (резерв) | `1s` |

Обязательные параметры — `SERVER_ADDRESS`, `BASE_URL`, `LOG_LEVEL`. Ключ
`SIGNING_KEY` задаётся **только** переменной окружения; при его отсутствии сервис
не падает, а подставляет резервный ключ — эта ветка существует для автотестов
платформы, которые стартуют со значениями по умолчанию. В реальной эксплуатации
задавайте `SIGNING_KEY` явно.

### Подключение к PostgreSQL

Строка подключения передаётся в формате DSN, например:

```
postgres://url_shortener:SECRET@localhost:5432/url_shortener?sslmode=disable&pool_max_conns=10&pool_max_conn_lifetime=30m&pool_min_conns=2&pool_max_conn_idle_time=5m
```

Пул `pgxpool` создаётся с проверкой доступности (ping с таймаутом 3 секунды).
Поддерживаемые параметры пула — стандартные для pgxpool (`sslmode`,
`pool_max_conns`, `pool_min_conns`, `pool_max_conn_lifetime`, `pool_max_conn_idle_time`).

### Параметры, не задаваемые извне

Следующие параметры заданы в коде и не конфигурируются через env или флаги:

| Параметр | Значение | Описание |
|---|---|---|
| `ShutdownTimeout` | 10 с | Таймаут graceful shutdown HTTP-сервера |
| `CookieUserIDTTL` | 24 ч | Время жизни cookie с JWT |
| `MinTokenLength` | 6 | Минимальная длина токена (base62) |
| `MaxTokenLength` | 10 | Максимальная длина токена |
| `BytesToGenerate` | 6 | Случайных байт на одну попытку генерации |
| `MaxGeneratingAttempts` | 10 | Попыток генерации на один токен |
| `MaxStoringAttempts` | 10 | Попыток сохранить при занятых токенах |
| `DeletionQueueBuffer` | 1024 | Глубина канала очереди удалений |
| `DeletionBatchSize` | 1024 | Размер батча асинхронного удаления |
| `DeletionQueueFlushTimeout` | 10 с | Период сброса батча удалений |
| `DeadLetterLogFile` | `emergency_dead_letter.log` | Файл потерянных пар (токен, пользователь) |
| instance lock (БД) | 20260101 | Ключ `pg_try_advisory_lock` |
| `auditCloseTimeout` | 10 с | Дедлайн доставки аудита при остановке |

## Миграции базы данных

Миграции SQL встроены в бинарник (`//go:embed *.sql`) и применяются автоматически
при запуске в режиме БД — отдельной команды не требуется. Файлы — в каталоге
`migrations/`: instance lock захватывается **до** накатывания миграций,
поэтому два инстанса не смогут применить их параллельно.

Схема базы данных включает две таблицы:

- **shorten_urls** — сокращённые ссылки с токеном, исходным URL, владельцем
  и признаком мягкого удаления;
- **users** — пользователи (UUID генерируется на стороне БД).

Подробно — в [ARCHITECTURE.md](ARCHITECTURE.md), раздел «Схема базы данных».

## Тестирование

Проект покрыт юнит-тестами во всех содержательных пакетах. Тесты используют
`testing` с библиотекой `testify` (`assert`, `require`, `suite`) и Table Driven Test.

### Команды Make для тестов

```bash
make test                              # все юнит-тесты
make test-v                            # с verbose-выводом
make test-pkg PKG=./internal/handler   # один пакет
make test-integration                  # интеграционные (нужен PostgreSQL)
make cover                             # итоговый процент покрытия
make cover-html                        # HTML-отчёт покрытия
```

### Ручной запуск тестов

Перед первым запуском: `go mod tidy`. Все юнит-тесты:

```bash
go test -cover ./...
```

Один пакет:

```bash
go test -v -cover ./internal/service
```

### Структура тестов

| Пакет | Инструмент мокирования | Подход |
|---|---|---|
| `internal/repository` | `pgxmock/v4` — мок pgx | Table-driven (suite); транзакции — через `ExpectBegin`/`ExpectCommit`/`ExpectRollback` |
| `internal/repository` (integration) | живой PostgreSQL | build tag `integration`, xmax-семантика на реальной БД |
| `internal/service` | mockery-моки интерфейсов `Storage` | suite; ретраи, откаты, очередь удалений, dead-letter |
| `internal/handler` | mockery-моки `Shortener` + `httptest` + resty | матрица маршрутов на реальном сервисе + мок-тесты ошибочных путей |
| `internal/audit` | `httptest.Server`, тестовые приёмники | suite; Broadcaster, дроп-счётчик, graceful stop |
| `internal/auth` | не требуется (чистая логика JWT) | testify assert |
| `internal/encoding` | не требуется (чистая функция) | Table-driven |

### Мокирование БД (pgxmock)

Для тестов слоя хранилища используется [pgxmock v4](https://github.com/pashagolub/pgxmock) —
мок pgx, не требующий реального подключения к PostgreSQL. Хранилище работает через
приватный интерфейс `dbtx`, который реализуют и `*pgxpool.Pool`, и мок pgxmock, —
поэтому тесты подменяют соединение без изменения кода. Каждый тест проверяет
ожидания через `mock.ExpectationsWereMet()`.

### Моки интерфейсов (mockery)

Для мокирования сервисного и хендлерного слоёв используется
[mockery v3](https://vektra.github.io/mockery/). Конфигурация — в `.mockery.yaml`
в корне проекта; моки генерируются в каталог `mocks/` рядом с тестируемым пакетом.

```bash
go install github.com/vektra/mockery/v3@latest
mockery          # из корня проекта, или: make mocks
```

Ключевые сгенерированные моки:

| Файл | Интерфейс |
|---|---|
| `internal/service/mocks/mock_Storage.go` | композитный `service.Storage` (все операции хранилища) |
| `internal/handler/mocks/mock_Shortener.go` | композитный `handler.Shortener` (все операции сервиса) |
| остальные `mock_*.go` | мелкие интерфейсы обоих слоёв |

Моки используют стиль `EXPECT()`. Незапланированный вызов метода мока роняет
тест паникой — «сервис вызван незапланированно» видно сразу.

### Интеграционные тесты

Интеграционные тесты репозитория (`pg_storage_integration_test.go`) живут под
build-тегом `integration` и требуют живого PostgreSQL. Запуск:

```bash
make test-integration
```

или вручную:

```bash
go test -tags=integration -run TestPgStorage_Integration ./internal/repository/
```

Тесты поднимают свою схему и проверяют семантику xmax-трюка на реальной БД,
включая сохранение точной копии удалённой строки.

### Подсчёт покрытия

Профиль покрытия собирается командой `go test -coverprofile`. Сгенерированные моки,
точка входа и пакет `migrations/` исключаются из подсчёта:

```bash
go test -coverprofile=coverage.out ./...
grep -v -e '/mocks/' -e '/cmd/shortener/' -e '/migrations/' coverage.out > coverage_filtered.out
go tool cover -func=coverage_filtered.out | tail -1
```

То же через Make: `make cover`, `make cover-html`.

### Бенчмарки

Бенчмарки живут рядом с обычными тестами в четырёх пакетах
(`internal/encoding`, `internal/service`, `internal/repository`,
`internal/handler`) в файлах `*_bench_test.go`. Запуск всех сразу:

```bash
make bench
```

Команда отключает юнит-тесты (`-run='^$'`) и прогоняет только бенчмарки
с подсчётом аллокаций (`-benchmem`). Для статистически надёжного сравнения
«до/после» используйте повторные прогоны и `benchstat`:

```bash
go test -run='^$' -bench=. -benchmem -count=10 ./internal/service/ > bench_after.txt
benchstat bench_before.txt bench_after.txt
```

Один бенчмарк с подбенчмарками — по имени:

```bash
go test -run='^$' -bench='BenchmarkStore' -benchmem ./internal/repository/
```

### Генератор нагрузки (cmd/loadgen)

`cmd/loadgen` — отдельная утилита (только stdlib), имитирующая реальную нагрузку
на работающий сервис. Три режима: `post` (создание ссылок — основной режим
для heap-диффов), `get` (редиректы по существующим токенам), `batch`
(пакетное создание ссылок). Ключевые флаги: `-mode`, `-n` (число запросов
измеряемой фазы; длительность прогона — производная), `-c` (воркеры),
`-seed`, `-batch`, `-warmup` (прогрев требует ответ 201 — любой не-201
останавливает утилиту); полный перечень и значения по умолчанию —
`./bin/loadgen -h`.

Пример прогона (адрес сервиса задаётся флагом `-base`):

```bash
make loadgen
./bin/loadgen -mode post -c 8 -n 20000 -seed 1
```

Ключевые свойства:

- **детерминизм — сиды и его предел** — сиды измеряемой фазы выводятся из
  `-seed`; это делает корректным сравнение benchstat-результатов и heap-снимков
  (разность снимков — `go tool pprof -diff_base`). Оговорка: при `-c > 1`
  распределение заданий между воркерами — гоночный фактор, множества URL
  двух прогонов совпадают лишь частично (при `-c=4` — около 94%); для строгого
  воспроизведения состава используйте `-c=1`;
- **прогрев требует 201** — повторный прогон того же сида на живом сервере
  упадёт на 409 в прогреве: перед повторным get-прогоном сервер перезапускается;
- **разделение пространств URL** — URL прогрева живут на хостах `*.seed`,
  измеряемой фазы — на `*.bench`, пересечений и ложных конфликтов 409 нет;
- **редиректы не уходят наружу** — за ответом 307 генератор не следует.

Для heap-профилирования сервис запускается с переменной окружения
`PPROF_ADDR` (например, `PPROF_ADDR=localhost:6060`): при её наличии стартует
отдельный HTTP-сервер с `net/http/pprof`; переменная не задана — сервер не
запускается, поведение сервиса не меняется. Снимок heap:

```bash
go tool pprof http://localhost:6060/debug/pprof/heap
```

### Запись измерений

Каждый прогон фиксируется в [MEASUREMENTS.md](MEASUREMENTS.md): базовая линия
(`make bench | tee bench_before.txt`, нагрузочные прогоны с фиксированным сидом),
правила корректного сравнения (одна переменная за раз, машина в простое,
benchstat только по повторам) и по блоку на каждого кандидата оптимизации
с полями «ожидание — дельта — вывод».
